## 摘要

在基于交互式 Coding Agent（Pi）对接 `gemini-3.8-flash` 的实际测试中，观察到了非常典型的**缓存命中剧烈波动**与**首字延迟（TTFT）断崖式暴涨**现象。

本报告基于调用日志、Google 官方文档，复盘该现象可能的技术成因，横向对比 Google、Anthropic、OpenAI 三家的缓存架构，并给出工程建议。

**更新（二次验证）**：之后把 Google Antigravity CLI（`agy` 1.4.2）作为 Claude Code 的子代理，在同一台机器上对 Gemini 4 Argon、Gemini 3.8 Flash 和 Claude Sonnet 5.5 做了复测（见第四节）。结论有三点变化：

- ~5.36k 的"保底命中"在一个系统提示完全不同的 Agent 上同样出现，初版"它等于当前工作区系统提示 + 工具定义"的解释站不住。
- Gemini 的命中窗口不是一个固定的 30~60 秒，波动很大。
- Claude 的缓存在跨进程、跨会话时同样稳定，进一步支持了初版"编程 Agent 优先 Claude"的结论。

复测中写成的子代理 skill 已开源：**[flyfishchen/antigravity-subagent](https://github.com/flyfishchen/antigravity-subagent)**。

## 一、实测现象复盘与时间轴流水

在本会话连续交互中，上下文长度逐步累积至 4 万 ~ 7 万 tokens，实测请求表现出**极其严格的"二分规律"**：

| 请求序号 | 触发场景 | 距上一请求间隔 (Diff) | 上下文总长 | 缓存读取 (cacheRead) | 命中率 | 开发者体感 |
| :---: | :--- | :---: | :---: | :---: | :---: | :--- |
| **01~12** | 初始对话与工具探索 | 2 ~ 13 秒 | < 19k | **0** | **0%** | 早期前缀处于冷启动期 |
| **13~16** | 连续工具调用链 | 2 ~ 12 秒 | 40k ~ 49k | **18,309 → 41,990** | **85%~92%** | 首字极快，缓存稳定累积 |
| **17** | **等待用户输入新问题** | **81.7 秒** | **49,827** | **5,357** | **~10% (断崖)** | **光标悬停数秒，明显卡顿** |
| **18** | 工具执行完毕返回 | **8.1 秒** | 51,967 | **47,212** | **90.8%** | 首字瞬发，瞬间回升 |
| **19** | **等待用户输入新问题** | **52.3 秒（< 1分钟）** | **52,701** | **5,369** | **~10% (断崖)** | **再次严重顿挫** |
| **20~23**| 工具连续链式调用 | 4 ~ 12 秒 | 54k ~ 62k | **50,054 → 56,240** | **90%+** | 连续高频命中 |
| **24** | **等待用户输入新问题** | **98.5 秒** | **63,077** | **5,439** | **~8% (断崖)** | **再次严重顿挫** |
| **25~31**| 工具链自动执行 | 3 ~ 8 秒 | 64k ~ 73k | **60,407 → 70,451** | **96%+** | 高速流式输出 |

## 二、核心技术成因分析

针对上述实测数据中的异常点，可能的根因可归纳为以下四层。其中第 2、3 点是推测，第四节的复测对第 3 点做了修正。

### 1. Google「隐式缓存」的机制局限
查阅 Google 官方文档（`https://ai.google.dev/gemini-api/docs/generate-content/caching?hl=zh-cn`）：
* **官方定性**：隐式缓存（Implicit Caching）默认开启，**官方明确声明"不保证节省费用（Best-Effort）"**，并建议***"尝试在短时间内发送具有相似前缀的请求"***；
* **易失性**：从本次数据看，用户停顿 52 秒以上后，会话特有的长历史就不再命中，空闲窗口大约在 30~60 秒量级。这是实测推断，官方没有给出具体数值；第四节的复测显示这个窗口并不固定。
* 这解释了为什么在工具调用链（间隔 3~12 秒）中能够跑满 7 万 tokens 的超高命中，而用户停顿思考一次就会掉回保底值。

### 2. 连接空闲与推理集群调度漂移（推测）
即使所有请求都发往**同一个 API 入口**，Google 庞大的云端架构也可能造成漂移：
* **连续调用时（< 15秒）**：连接保持存活，请求大概率落到持有该会话 KV Cache 的同一批实例上；
* **用户停顿思考时（> 45秒）**：连接空闲关闭后，新请求可能被调度到没有该会话缓存的实例上。

### 3. 为什么命中数精准回落到 ~5,357 tokens？
在每一次断崖下跌中，`cacheRead` 既不是 0，也不是从第 4 万 token 处断开，而是**极其精准地维持在 5,357 ~ 5,488 tokens**。

* **初版解释**：5,357 tokens 恰好是当前工作区 System Prompt + Tools 的静态基准大小，属于多租户共享的热点前缀，各节点常驻缓存。
* **复测修正**：在 Antigravity CLI 上用 Gemini 4 Argon 复测，保底命中是 **5,362 ~ 5,739 tokens**，几乎是同一个数。可 agy 的系统提示和工具定义与 Pi 完全不同，它每次请求的固定前缀约 7.4k tokens，也不是 5.36k。两个不同的 Agent 得到几乎相同的保底值，说明它更可能来自平台侧（例如缓存的块粒度，或服务端注入的公共前缀），而不是"当前 Agent 的系统提示"。具体机制仍待验证。
* 不变的结论是：**缓存并不是"格式损坏导致截断"。会话特有的长历史在漂移或过期后完全失效，只剩一段固定的公共部分保底命中。**

### 4. 首 Token 延迟（TTFT）巨大的机理
* **缓存命中时**：仅需对最新输入的少量 token 做前向计算，TTFT < 1s，体感瞬发；
* **缓存失效时（Cache Miss）**：必须对 5 万 ~ 7 万 tokens 重新做全量预填充（Prefill），导致用户敲下回车后**光标悬停 5 ~ 15 秒**，交互流畅度被彻底破坏。

## 三、主流模型厂商上下文缓存架构横向对比

> Anthropic 一列已按 2026 年 10 月的官方资料更新；Google、OpenAI 两列以及各家 TTFT 数值沿用初版，未在本次复测中核实。

| 评估维度 | Google Gemini (隐式 / 显式) | Anthropic (Claude Opus 5.5 / Sonnet 5.5) | OpenAI |
| :--- | :--- | :--- | :--- |
| **缓存机制** | **双轨制**：<br>① 隐式：自动、Best-Effort、易失<br>② 显式：独立对象、手动建删、需付费 | **显式断点 + 自动缓存**：<br>`cache_control: { type: "ephemeral" }` 断点，或请求级自动缓存；最小可缓存前缀 512 tokens | **全自动前缀匹配** |
| **缓存保留期 (TTL)** | 隐式：**几十秒量级，不固定**<br>显式：**默认 1 小时**（按需指定） | **默认 5 分钟**，每次命中免费续期；可选 **1 小时** | **~5-10 分钟**（自动滑动续期） |
| **上下文上限** | **1,000,000 ~ 2,000,000 tokens** | **1,000,000 tokens** | 128,000 tokens |
| **计费规则** | 命中享 **75% 折扣**<br>（显式需额外收存储费） | 读约 **0.1x**（Opus 5.5 为 0.05x）<br>写 **1.25x**（5 分钟）/ **2x**（1 小时），无存储费 | 命中享 **50% 折扣**（输入 0.5x）<br>（无额外写入与存储费） |
| **TTFT 表现** | 命中时良好（~1s）；<br>**失效时断崖暴涨（8~15s+）** | 命中时极快（~500ms）；<br>失效时平滑（~2-4s） | 命中时极快（~600ms） |
| **多模态缓存** | **全格式原生多模态**（超长视频、音频、PDF、大图） | 文本、图片、PDF | 文本、图片 |
| **最适业务场景** | **超长上下文只读知识库、音视频多模态分析** | **Coding Agent、交互式多轮对话、高频代码重构** | **通用多轮对话、高吞吐标准 API 服务** |

### 对比结论
1. **在 Coding Agent / CLI 领域，Anthropic 体验优势明显**：
   5 分钟、命中即续期的窗口契合人类读代码、敲代码、思考打字的节奏，加上约 90% 的读折扣。第四节的复测里，经 agy 调用的 Claude 命中率稳定在 95% 以上，跨进程也能命中。
2. **Google 的架构重心在"超长上下文与共享资料库"**：
   Google 的显式缓存（`cachedContents`）本质上是一个持久化的云端文档，适合大量并发请求反复检索同一份静态资料，或对长视频做高频问答。但它**不可追加、按小时收存储费、需冷启动建仓**，不适配每轮都在追加内容的 CLI 工具。

## 四、二次验证：用 Antigravity CLI 作为子代理复测

### 测试方法
* **工具**：Google Antigravity CLI（`agy` 1.4.2），以无头模式 `agy -p --output-format stream-json` 运行，从每一步的 `usage` 中读取 `input_tokens` 与 `cache_read_tokens`（两者之和为该步的提示词总量）。
* **场景**：由 Claude Code 把 agy 当作子代理调用，任务是读写几个小文本文件，上下文约 7k ~ 17k tokens。
* **两种调用方式**：
  * 单进程多轮：`--input-format stream-json`，同一进程连续跑 3 轮，每轮 2 步；
  * 跨进程续接：每次新开进程，用 `--conversation <id>` 续接。
* **说明**：经 agy 调用的 Claude 模型走的是 Google 的通道，费用按 Google 的规则计，下文只看缓存命中，不讨论价格。

### 结果一：单进程多轮（请求间隔 2~10 秒）

| 模型（经 agy） | 首步 未命中 / 命中 | 后续各步 未命中 / 命中 | 结论 |
| :--- | :---: | :---: | :--- |
| `gemini-3.8-flash-low` | 7,428 / 0 | 7,568~8,298 / **0** | 小上下文下完全不命中 |
| `gemini-4-argon-low` | 7,416 / 0 | ~2,100~2,300 / **5,362~5,739** | 只命中 ~5.36k 的固定部分 |
| `claude-sonnet-5-5-low` | 11,531 / 0 | 108~527 / **11,243~12,708** | 命中率 95% 以上 |

### 结果二：跨进程与续接
* **Claude**：一个**全新进程**的第一步就有 `cache_read = 40,365`，因为前几分钟其他 agy 调用已经写入了相同的前缀；用 `--conversation` 续接后 `cache_read = 64,920`。在 5 分钟、命中即续期的 TTL 内，只要前缀字节完全一致，缓存就能跨进程、跨会话共享。
* **Gemini 3.8 Flash**：未观察到任何跨进程命中。
* **Gemini 4 Argon**：约 2 分钟后续接（约 17k 上下文），`cache_read = 12,426`，命中 72%；同模型单进程两轮合计只有 54%。命中量波动很大。

### 复测带来的修正与补充
1. **保底命中不是"本工作区的系统提示"**：见第二节第 3 点。
2. **Gemini 的命中窗口不固定**：Pi 实测中停顿 52 秒即掉回保底；而 agy 上的 Argon 隔了约 2 分钟仍命中 72%。"30~60 秒 TTL"只能当作经验区间，不能当成规格。
3. **小上下文 + 短间隔也不保证命中**：Flash 在约 8k 上下文、2~3 秒间隔下一次都没命中，与 Pi 实测中请求 01~12（< 19k）全部为 0 一致。隐式缓存似乎还要求上下文足够长或经过预热，不只是"短时间内发相似前缀"。
4. **Agent 自身的开销不可忽视**：agy 每次请求的固定前缀约 7.4k（Gemini）/ 11.5k（Claude）tokens，进程启动 + 鉴权约 3~10 秒；一个只统计文件数的小任务，agy 甚至自己又开了子代理，总消耗 58k tokens。

## 五、把 agy 接成 Claude Code 子代理：权限上的坑

复测时顺手把 agy 封装成了 Claude Code 的 skill。缓存之外，权限问题比预想的多：

* **子代理绕过了主代理的权限检查**：在 Claude Code 看来只是执行了一条命令，agy 随后读写了什么、跑了什么命令都不经过 Claude Code 的审批。
* **测试机上 agy 实际不受任何限制**：CLI 设置为 `always-proceed`，无头运行可以写工作区外的文件、写 `$HOME`、访问外网。
* **终端沙箱在 Ubuntu 上不可用**：AppArmor 默认禁止非特权 user namespace（`kernel.apparmor_restrict_unprivileged_userns = 1`）。此时 `--sandbox` **不报错也不生效**，`--mode auto` 打印警告后退回默认模式。
* **唯一可靠的控制点是 PreToolUse hook**，但有几个细节：
  * `~/.gemini/antigravity-cli/hooks.json` 会被加载，里面的 hook 却不执行；`~/.gemini/config/hooks.json` 和 `<workspace>/.agents/hooks.json` 会执行。
  * hook 输出为空或 `{}` 时**按拒绝处理**，"中立"必须显式返回 `{"decision":"ask"}`。
  * hook 超时也按拒绝处理；hook 阻塞时 agy 会一直等待，理论上可以做实时审批。
  * 被拒后 agy 常常换别的工具绕过，比如 shell 被拒就改用 read_file。

基于这些结论，skill 里实现了 `readonly / workspace / full` 三档策略，并把拒绝分为三类：

* **硬拒绝**：凭据、提权、管道到解释器等，任何授权都放行不了；
* **待审批**：经用户同意后，用 `--grant cmd:<精确命令>` / `write:<路径>` / `tool:<工具名>` 放行，并续接同一会话；
* **交给主代理**：git commit / push 由 Claude 审完 diff 后自己执行。

代码、实测记录和单元测试见 **[github.com/flyfishchen/antigravity-subagent](https://github.com/flyfishchen/antigravity-subagent)**。

## 六、工程落地与解决方案

### 方案 A：开启 Pi 客户端 Cache Warming
Pi 内部未接入 Google 的 `cachedContents` 显式缓存接口（因其不支持动态多轮追加），但提供了 **Cache Warmer（空闲保活机制）**：

1. 在 `~/.pi/agent/settings.json` 中配置：
   ```json
   {
     "cacheWarming": "idle"
   }
   ```
2. 在 `~/.pi/agent/models.json` 对应的 `gemini-3.8-flash` 模型中声明短寿命：
   ```json
   {
     "id": "gemini-3.8-flash",
     "promptCache": {
       "short": 30,
       "long": 300
     }
   }
   ```
* **效果**：检测到用户停顿接近 25 秒时，Pi 会在后台以 `maxTokens: 1` 发送微型心跳，以很低的代价维持跨轮次命中，消除 10 秒以上的首字卡顿。考虑到第四节观察到的波动，保活只能提高命中概率，不能保证命中。

### 方案 B：编程模型选型建议
* **高频交互 / 重构阶段**：优先选用 **Claude Sonnet 5.5 / Opus 5.5**，利用 5 分钟命中即续期的缓存和快速的 TTFT，保证开发心流不被打断；
* **超大上下文导入阶段**：需要一次性灌入整仓代码、大型依赖库或音视频资料（> 200k tokens）时，切换到 **Gemini** 发挥其超大容量与低成本优势。

### 方案 C：把 Gemini 当子代理用时的调用策略
* **同一任务的多轮追问放进一个进程**（stream-json 输入），不要隔很久再用 `--conversation` 续接；
* **Gemini 适合"一次喂大上下文、一次出结论"**的阅读型任务；需要反复迭代的小改动交给 Claude；
* **以实测为准**：以每次调用实际返回的 `cache_read` 为准，不要假设一定命中；
* **先划好权限边界再派活**：见第五节。

以上策略都已写进 [antigravity-subagent](https://github.com/flyfishchen/antigravity-subagent) skill。
